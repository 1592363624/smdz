# 主进程交叉验证发现（供合并时校对子代理报告）

记录主进程独立核查的结论，子代理报告中如有冲突，以此为准并标注。

## 发现 1：手动「开采」语义差异（重大 🟡）
- 原版 _主程序.ecode L7491「开采」：**载具开采**。门禁：需驾驶载具→载具 HP>0→载具部件要求（引力调频器 g2=3 / 行星解裂器 g2=2 / 激光采集器 g2=1，均无则提示安装并给「1@制造部件」临时替换）→不能是副本→行动无限制（理由5，工作60秒标记）→无隐形模块时新建延时覅攻击pd 5秒（引怪）→玩家活跃→新建延时「开采1c2c」60秒结算（L7534）。
- 新版 handleMine（game.service.ts L3250）：直接采当前地图 resources2 资源点（有 amount 的资源），无载具要求、无采集器要求、无 60 秒延时、无引怪。冷却用 markers2 mine_地图id_资源名 + respawnTime(默认300秒)。
- 新版 auto-mine.service.ts：**已完整复刻原版「开采」语义**（getContext 采集器三档、validate 需要载具/不能在副本、隐形模块豁免、跟随因子 min(2,followers)+1），但挂在「开采自动/开采停止」路径。
- 结论：新版「开采」指令行为与原版不同（简化成直接采资源点）；原版「开采」的载具轰炸玩法只在自动开采中保留。需确认是有意设计还是迁移遗漏。原版 L7534「开采1c2c」60秒延时结算链在新版无对应。

## 发现 2：补魔语义差异（🟡 较大）
- 原版 L7110「补魔」：门禁=需「躺下」成就状态（躺下中）→ 地图必须是自家房子「屋内」→ 召唤物跟随显示(2)（有跟随对象，取对话7）→ 补魔间隔 21600 秒冷却 → 添加标记工作35秒 → 新建延时「覅b魔w成」30秒结算（L7158）。
- 新版 handleRefill（game.service.ts L10190）：背包找「魔力药剂/魔力药水」→扣1瓶→markers['魔力']+50 上限500。完全不同的实现（无躺下/屋内/跟随对象/延时结算）。
- 结论：新版是自创简化实现，注释虽写「对应原版：补魔命令」但行为完全不同。原版是「与召唤物补魔」（涩涩玩法），新版是喝药。差异显著，标 🟡/❌。

## 发现 10：维修语义差异（🟡 较大）
- 原版 L10397「维修」：无参=维修自己驾驶的载具。门禁：行动无限制(理由6)→未驾驶→地图战斗增益+有怪→死亡→取载具(计算载具)→弹射（编号0）→部件超上限四类拦截→生命满→「还不需要修」。执行：a=20 秒，载具部件要求（小雫/小凰/小蓝/小粉 各 -5 秒）→a<1 即时用 0 载具零件修好（成就维修载具+1）；否则「正在维修X,大概需要N秒」+工作标记(a)+新建延时「维修wcc1」a秒结算。
- 新版 handleRepairVehicle（game.service.ts L9522）：维修工具（恢复50%）或 100 经验（恢复30%）即时修。无 20 秒延时、无小雫/小凰/小蓝/小粉减时、无载具零件消耗、无战斗中断条件。
- 新版无「维修wcc1」延时链。🚩 载具零件作为维修材料在原版消耗、新版不消耗。
- 另外注意新版「修理」case（handler L1491 附近）路由到 handleRepairItem（修物品），与原版「修理」L7012 是「修理武器」（武器破损系统？）可能也不同，待子代理详查。

## 发现 11：发射信号枪语义差异（🟡）
- 原版 L6281「发射信号枪 N」：消耗 N 把信号枪→10秒冷却→「发射了信号枪……」→成就召唤货舱+1→活跃度+1→新建延时「召h货1藏」+N 6秒→「召h货1藏」结算：消耗对应数量信号枪生成货舱到地图。
