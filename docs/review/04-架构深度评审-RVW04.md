## 一、总体结论

**定性判定：架构健康且方向正确（PASS with concerns），可以支撑项目继续演进——但"防御性基础设施"的复杂度正在逼近收益拐点，且缺乏 CI 强制力。** 骨架层（写入一致性）已完成从"救火补丁"到"纵深防御 + 架构门禁"的升级：玩家域写路径已收敛为 Actor 单写者（legacy 双轨于 2026-09-08 删除，有门禁防回退），货币列化、延时任务持久化、PM2 单实例等 RVW02 疑虑均已落地。当前最大的两个结构性风险：① game.service.ts 在评审期间仍在**净增长**（15,222 → 17,296 行，256 个业务方法、28 个构造依赖），God Service 问题不是存量而是增量；② 全部质量护栏（109 个 spec、21 条架构门禁）**不在 CI 中执行**，规范靠开发者自觉，这与"文档会丢、测试不会丢"的项目哲学自相矛盾——测试也有了，但没有变成门禁。

### 数据模型专项结论

Player 现为 17 个 Json 列（schema.prisma:133-151）+ 关系列混合。"快照回写模式"的历史踩坑（bba6e77 好感丢失、07d3dfb markers 增量覆盖）根因均为"子流程自持局部快照"，现已被 mutate 上下文（唯一快照复用）+ 写基线 diff + version CAS 三层根治，且各自有门禁/测试固化——**这不是"暂不重构"，而是"已系统性缓解"**，判定升级。剩余风险：Actor 内业务直接持有 cell.state 活态引用（player.service.ts:443 peekLive），绕过任何 diff 直改，正确性依赖 markDirty 纪律（架构上无强制），但该纪律已被门禁与代码注释多重强调，实际风险低。宽文档写放大是结构性成本，在单机+串行写前提下可接受；若未来性能数据支持，按"货币列化"先例优先把 backpack/equipment 列化即可，无需全面关系化。

2. **CAS 升级决策**（P1-3）：查询生产日志中"玩家乐观锁冲突"与"拦截到旧快照整包写入"的出现频率；若连续 1-2 周为零（单进程+邮箱收敛后理论上应为零），将 PLAYER_WRITE_CAS 默认值翻为 strict，把最后一道防线从"可观测"变"可阻断"。

### 短期（1-2 迭代）

## 五、专项评估①：Actor 迁移主线

**方向判定：正确，且是本仓库近期最高质量的架构工作。** 理由：① 与部署形态自洽——PM2 单实例 fork（ecosystem.config.js:13）与"单进程 Actor"假设（actor-runtime.ts:27-29 明示水平扩容需分布式邮箱/亲和路由）互相印证，没有过度设计；② 迁移完成度在玩家域是真实的 100%（写路径唯一、双轨删除、门禁固化三件套齐全），不是口头迁移；③ 设计细节（ALS 随 setTimeout 逃逸→isRunActive 双重判定、mutate 上下文 finish 收口防死上下文吞写）都来自真实事故复盘并有对应测试（mutate-als-timer-leak.spec.ts 等）。

**优先级排序建议：**
1. **P0：收尾玩家域，把收益收满**——CI 门禁（建议 1）、CAS strict 升级（建议 2）、写 API 收敛（建议 9）。Actor 迁移的"最后一公里"不在代码在流程。
2. **P2：冻结 map/monster 域的 Actor 化**——不再横向铺开（建议 5）。withMapLock 闭环 + diff 写回 + 门禁已提供等效串行保证，Actor 化地图/怪物的边际收益（免重读）远小于引入双锁认知成本。
3. **不做：vehicle/shopitem Actor**——无并发热点证据，纯投机性注册。
4. **未来触发点**：仅当出现"多实体原子写"硬需求（玩家间交易、公会银行）时启用 coordinate()，并此时必须给 coordinatorTimeoutMs 配非零默认值（当前 0=永不超时，actor.module.ts 传空配置 {}）。

**风险清单：** ① ALS 逃逸类 bug 会换马甲复发——现有专项测试偏薄（mutate-als-timer-leak.spec.ts 仅 1 个 it），建议补"邮箱内调度定时器→回调写→落库验证"的参数化用例；② 内存上限：lruMax=2000 cells × 宽行（17 JSON 列，重度玩家单档可达数十~数百 KB），与 max_memory_restart 300M 的组合偏紧，建议按真实玩家档体积压测后校准 lruMax 或上调内存阈值；③ 单进程意味着重启丢"在途 run"——writeThrough 策略下窗口极小（毫秒级），可接受，无需改 deferred（deferred 有崩溃丢账风险，与本项目"安全优先"取向相悖，不建议开）。

## 六、专项评估②：game.service.ts 拆分策略

**总原则：按指令域拆、不动写入机制、每次拆分跑全量测试。** GameService 保留为「指令路由外观 + 共享基础设施」（mutatePlayer 薄封装、推送防抖、延时任务 handler 注册），目标 ≤3,000 行；子 service 之间**禁止互注**（都只依赖数据层服务 + PlayerMutateService + 通用 util），避免拆完从上帝类变成网状类。

**按现有 256 个 handle/apply/settle/complete/perform 方法的实际分布，建议切 6 块：**

| 子 service | 承接内容（现有方法簇） | 预估规模 |
|---|---|---|
| map-command.service | handleMove/handleTeleport/handleFlyTo/handleArriveAt/performArrival 族/handleMap/getMapOverview/getNearbyPlayers/采集到达触发 | 大 |
| gather-mine.service | handleGatherResource/settleGatherResource/handleMine/settleManualMine/mineByVehicle（与 auto-mine.service 合并考虑） | 中 |
