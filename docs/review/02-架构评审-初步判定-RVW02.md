## 总体判定：**CONCERNS（可上线，但有明确的应修项）**

骨架是健康的：NestJS 标准分层、Prisma + MySQL、模块化 service、写入一致性机制健全。问题集中在**代码集中度**与**数据无契约**两点，且二者相互放大。

## A. 数据层（schema.prisma，509 行，16 模型）

### 正面
- ✅ **写入一致性机制健全**：`player-mutate.service.ts` 全程持 `PlayerService.enqueueUserWrite` 用户级串行锁，与战斗、后台结算互斥；`Player.version` 乐观锁（schema 第 10 行）；只读指令不落库、不自增 version（`player-mutate.service.ts:9,82,92,128`）。这在并发指令场景下是正确的设计。
- ✅ CurrencyLog / CommandLog / DelayedTask 等审计模型存在，有可回溯性。

### 风险
- ⚠️ **Player 单行宽 JSON 文档模式**：Player 模型含 **14 个 Json 字段**（backpack / equipment / weapons / markers / markers2 / buffs / tasks / titles / skills / sets / bonus / baseBonus / safeBox / equipmentPresets），注释直接对应原版易语言数组（[物品3]、[装备]）。影响：
  1. 任意玩法（任务进度、增益、背包、称号）的写入都触发**同一行的读-改-写**，行越大写放大越大；
  2. 所有玩法共享用户级串行锁，**并发上限 = 单玩家串行**，重度玩家多指令并发会排队；
  3. JSON 字段无 schema 校验 → 数据脏污（level 全 1、attack 全 10、称号三项全空）能静默入库。
  - **判定**：单机/小规模可接受，不必立刻重构；但应**先补 JSON 内容校验层**（启动时或 seed 时校验），并规划热数据（backpack/equipment）与冷数据（titles/markers）分表。
- ⚠️ **`dataCores` 字段存在但「数据核心」物品未定义**（见 RVW-01 §2.9）——Player.currency 与 items.json 出现双轨，同一资源两套表示，易产生不一致。

## B. 服务层（game 模块 53,795 行）

| 文件 | 行数 | 判定 |
|---|---|---|
| game.service.ts | **15,222**（约 220 个 async 方法） | **God Service，P1 必拆** |
| combat-system.service.ts | **10,949** | God Service，P1 |
| familiar-system.service.ts | 4,647 | P2（称号逻辑硬编码于 :3975~4119，随 P1-1 数据化时一并抽出） |
| familiar-skills.service.ts | 3,732 | P2 |
| item-system.service.ts | 2,720 | 可接受 |
| bonus.service.ts | 2,348 | 可接受（升级公式 :405 已定位，数值重构入口清晰） |

- 问题本质：**指令路由层（game-command.handler）把业务全部压进 game.service**，导致任何玩法改动都在 15k 行文件里找位置，回归风险随体积指数上升。
- **建议拆分方向**（按指令域拆，不动写入机制）：`game.service.ts` → task / shop / trade / mount-vehicle / pet / checkin / admin 等子 service，共用 `player-mutate` 上下文。每拆一块跑一次现有 jest 回归。

## C. 数据加载（static-data.service.ts，509 行）

- ✅ 懒加载 + 内存 cache（`:77,85,90`），`fs.readFileSync` 按需读 1.6MB JSON，启动压力小；有 cache 重置入口（`:107`）支持热重载。
- ⚠️ **无加载时校验**：JSON 结构异常（字段全 1、悬空引用）直接进 cache 被业务消费。**建议在此处加启动校验**（引用完整性 + 异常值告警），这是拦截 RVW-01/03 全部数据问题的唯一收口点，成本最低收益最大。
