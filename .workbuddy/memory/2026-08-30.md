## 文档：README 补充 GitHub Actions Secrets 说明

在 `README.md` 的「部署到 Windows 服务器」章节下新增「GitHub Actions Secrets 配置」小节，
用表格标注 6 个仓库 Secret 与项目文件的对应关系：

- `ENV_FILE` → `server/.env` 的完整内容（部署时经 `.env.upload` 覆盖写入服务器 `server/.env`）
- `WIN_APP_NAME` → `deploy/windows/deploy.ps1` 的 `-AppName`，即 PM2 进程名（如 `smdz-server`）
- `WIN_HOST` / `WIN_USER` / `WIN_SSH_KEY` → SSH 连接三件套，用于 `.github/workflows/deploy.yml`
- `WIN_PATH` → 服务器部署根目录，支持 `/c/wwwroot/smdz`、`C:/wwwroot/smdz`、`C:\wwwroot\smdz` 三种写法

关键约束：`WIN_HOST`/`WIN_USER`/`WIN_APP_NAME`/`ENV_FILE` 缺失时 deploy.yml 的 `require_value` 会直接报错退出。

## 功能：延时指令倒计时在 UI 上可视化（pendingActions）

**背景**：原版大量指令是「发指令 → 等 N 秒 → 延时结算」，期间玩家被行动限制锁住，界面只有聊天区一行文字，
玩家常误以为指令没生效而重复发送（如「打开箱子」后立刻又发「打开休眠仓」）。

**实现**：

- 后端 `server/src/modules/game/game.service.ts`
  - 新增私有方法 `buildPendingActions(player, markers, markers2)`，聚合所有「还需要 N 秒」的状态：
    采集 `markers['采集中']`（打开箱子/休眠仓/收集木头…）、移动 `markers['移动中']`（JSON 字符串，需二次解析）、
    markers2 中带 `rescueType` 的「复活/工作」（抢救使魔/维修载具/自救/救助玩家）、「麻痹」负面锁定。
  - 输出结构 `{key, kind, label, detail, icon, startedAt, endAt, totalMs}`，只保留未到期条目，按 endAt 升序。
  - `buildPlayerInfo` 新增 `pendingActions` 字段 → REST `/game/player/info` 与 socket `player:update` 同步覆盖。
  - 移动状态补写 `startedAt`（handleMove 与飞行两处），供前端算进度百分比。
- 前端 `web/src/components/PendingActionBar.vue`（新增）：本地时钟每秒 tick，渲染名称+剩余秒数+进度条，
  按 kind 配色（采集橙/移动青/救助绿/麻痹红），条目到期时 emit `expired`。
- `web/src/views/ChatView.vue`：组件插在 `messages` 与 `input-bar` 之间（固定不随滚动），
  `onPendingExpired` 做 1.5s 节流后重拉 playerInfo + mapOverview，清掉已结算条目。
- 测试 `server/test/pending-actions.spec.ts`（新增 9 例全过）。

**关键机制**（复用）：`PlayerService.savePlayer` → ChangeBus → `SyncProjectorService` → `pushPlayerUpdate`（300ms 防抖），
所以延时结算完成后无需手动推送，前端自动收到空 `pendingActions`。

**改动的坑**：`markers['移动中']` 存的是 JSON **字符串**（采集中是对象）；markers2 的 `expireAt` 有秒/毫秒两种口径，
必须 `>= 1e12` 判定归一；「采集」「移动」在 markers 与 markers2 里是镜像关系，需去重避免重复条目。

### 修复：部分倒计时「只读秒、进度条不动」

**现象**：采集时进度条正常推进，抢救/移动时进度条停在 0% 只有读秒。

**根因**：`buildPendingActions` 的 `push()` 里，抢救类条目只传了 `endAt`，没传 `startedAt`/`totalMs`；
而兜底式 `Math.floor(item.startedAt ?? 0) || Math.max(0, endAt - Math.floor(item.totalMs ?? 0))`
在两者都缺失时算出 `startedAt = endAt` → `totalMs = 0` → 前端 `percentOf` 直接返回 0，画出一条卡住的空槽。

**第一轮修复（走了弯路，已简化）**：去后端补 `startedAt`/`totalMs`，甚至正则反解 `rescue-<毫秒>-` 的 token。

**最终修复（用户的思路，正确）**：**有 `endAt` 就够了** —— 前端第一次渲染某条目时的剩余时间，
天然就是进度条的分母。在 `PendingActionBar` 里用一个 `observed: Map<key, {endAt, totalMs}>` 记住
首次观测值，之后 `percent = (total - remain) / total` 从 0% 走到 100%。判断重置的条件：
key 首次出现 / `endAt` 变化（新一轮操作）/ 剩余时间被延长。后端不需要任何额外字段，
历史数据、刷新页面、重连全部自然工作（刷新后从"看到的那一刻"重新起算，符合玩家感知）。

- 后端只保留顺手落盘的 `startedAt`/`totalMs`（采集/移动/抢救/麻痹），
  仅用于刷新后进度条落在真实位置；`totalMs = 0` 表示未知，前端自行兜底。token 反解已删除。
- `push()` 改为「起止时间与总时长知其二即可推第三个」，两者都拿不到时 `totalMs = 0` 显式表示未知（不再静默算错）。

**教训**：进度条不一定要「已完成 / 总时长」，用「观测起点 → 结束」同样成立，且不需要后端配合。
**先想清楚能不能在消费侧解决，再决定要不要改数据模型** —— 不要为了让某个 UI 字段"语义正确"去全链路补数据。

## Bug 修复：技能指令报「玩家数据并发冲突，请重试」（ex/歼灭/万象/日轮）

**现象**：玩家发 `ex` → 系统回「指令执行错误: 玩家数据并发冲突，请重试」，误以为技能坏了。

**根因**（`server/src/modules/game/familiar-skills.service.ts`）：
`castCombatSkill()` 内部会**自己再调一次** `getPlayerData` 读新快照，并在末尾 `savePlayer` 落库
（写冷却/技能经验/活跃度），db version 随之推进。而外层技能方法仍持**调用前**那份旧快照 A
继续 `addBuff` + `savePlayer`，CAS 用过期 version 匹配 → P2025 → 抛「并发冲突」。
乐观锁其实是救了数据：若真写进去，旧快照会把冷却/技能经验/活跃度整包覆盖回滚。

**受影响范围**（4 个技能，均在 castCombatSkill 之后续写保存）：
- `excalibur`（ex/誓约胜利之剑）— **无条件必现**（每次施放都报错）
- `annihilate`（歼灭）— 好感≥20 才触发
- `myriadVisions`（万象·军姬2）— 好感≥60 才触发，且回血基准用旧 hp 会把战损回滚
- `solarWheel`（日轮）— 场上有怪时触发；**附带发现**：漏了 `player.markers = JSON.stringify(markers)`，
  导致 `getFeather` 扣的羽毛根本没落库

未受影响：`criticalHit`/`fullSalvo`/`cannonCrown` 在 castCombatSkill 之后不再保存。

**修法**：
1. `castCombatSkill` 返回值由 `string` 改为 `{ result, player, markers }`，把内部已落库的最新快照交还调用方；
   冷却中提前 return 的分支同样返回三者。7 处调用点适配（3 处 `const { result }`、4 处取 `livePlayer/liveMarkers`）。
2. 4 处续写改用 `livePlayer/liveMarkers`，日轮补上 markers 回写。
3. `executeSkill` 整体包 `playerService.withUserLock(userId, ...)` 串行化，switch 抽成私有 `routeSkill`。
   真并发（与采集结算/地图战斗节拍互踩）也一并消除。锁可重入（ALS 检测同链），
   六道轮回内部再次 `withUserLock` 不会死锁。

**验证**：`npx tsc --noEmit` 通过；新增回归测试 `test/excalibur-burn.spec.ts` 的
「誓约胜利之剑 保存链路回归（旧快照不得续写）」；全量 jest 571 通过。
唯一失败 `integration-display-mult.spec.ts` 是连真实远程库的端到端用例 180s 超时，与改动无关。

**通用教训**：本项目的 `savePlayer` 走中央乐观锁 `(id, version)` CAS，**任何「读快照 → 调子流程 → 再改再存」
的链路都必须确认子流程有没有自己重新读档并落库**。子流程若会落库，必须把它的快照交还上层，上层不得沿用旧快照。
