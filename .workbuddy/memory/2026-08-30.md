## 玩家状态写入口「彻底根治」（Actor 式单写者）

延续上轮的基础设施安全网 + 指令漏斗方案，今天定位并修复了安全网本身的**致命反查键 bug**：

- **根因**：`PlayerMutateService.run` 把 mutate 上下文登记在 `userId` 下，但 `PlayerService.savePlayer`
  用 `currentFor(player.id)` 反查（`Player.id` 自增主键 ≠ `Player.userId`）。结果「在 mutate 内调用
  savePlayer」命中不到 ctx → 内层 savePlayer 真的写库并 bump version，外层保存再以过期版本 CAS →
  双写/版本分叉 → 正是反复出现的「玩家数据并发冲突，请重试」根因。
- **修复**：`run` 同时按 `userId` 与 `player.id` 登记；`savePlayer` 改按 `resolveMutateKey`
  （优先 userId，回退 player.id）反查合并。因 `AsyncLocalStorage.run` 在 fn 结束后还原 store，
  最外层收口仍走真实落库。
- **BigInt 加固**：`getPlayerData` 读侧把玩家对象上的 `BigInt` 属性（lastOpTime/readTime）转 Number，
  修掉 `pushState` 序列化抛「Do not know how to serialize a BigInt」的崩溃。

### 验证
- 新增回归测试 `test/player-mutate.spec.ts`「mutate 内业务方直接调用 savePlayer 应合并回上下文而非
  二次落库」；临时回退修正可复现 `prisma.update` 被调用两次（version 0→1、1→2），证明确为有效护栏。
- 全量单测（排除 integration）：**540/541 通过**（新增 1 个回归测试）。
- 唯一失败 `onboarding-flow`（真实远程库 e2e）卡在教程文案内容断言，环境相关，与并发修复无关。

### 经验教训
- 「上下文感知」类安全网必须保证**登记键与反查键一致**，否则静默失效（比没有安全网更危险，
  因为看起来已收口）。用「内层 savePlayer 应只落库一次」这类计数断言才能锁住。
- 指令路径与定时器（auto-mine / gather / weaponAttack）都走同一把 `withUserLock`，故已天然互斥；
  `settleGatherResource` 中段 CAS 认领是刻意的真实落库，勿并入 merge。

## 纯 Actor 单写者收口：无锁、无 CAS（用户质疑后）

用户指出：上一轮「彻底根治」声称参照 Actor/Orleans/Erlang（消灭并发、串行归属、每玩家一个串行队列、
内部单线程无竞态、**不需要锁也不需要 CAS**），但代码里仍叫 `withUserLock`（锁）且 `savePlayer` 仍有
`(id,version)` CAS 冲突判定——与纯 Actor 不符。选定方案：**路由2写者 + 移除 CAS**。

### 改造
- 命名纠偏：`withUserLock`→`enqueueUserWrite`（per-user Promise 链 = Actor 收件箱，**非互斥锁**）；
  `userLocks`→`userMailboxes`、`lockContext`→`mailboxContext`。8 个源码文件 + 12 个测试桩同步 rename。
- `savePlayer` 移除 CAS：删去 `where:{id,version}` + P2025→抛「玩家数据并发冲突」分支，改为普通
  `update({where:{id}, data})`；version 仅由 Prisma `$use` 中间件自增，`player.version=snapshotVersion+1`
  回写内存快照。无并发写（同用户全经邮箱），无版本分叉风险。
- `ScheduleService.settlePendingMoves` / `cleanupExpiredBuffs` 两条定时器裸写收口：
  `enqueueUserWrite(userId, async()=>{ getPlayerData 重读最新快照→改→savePlayer })`，达成全量单写者统一。

### 验证修复（原 2 失败 + 1 被 CAS 移除连带破坏）
- `architecture-guard`：`RAW_SAVEPLAYER_BASELINE` 217→219（schedule 两条 `prisma.player.update` 合规收口为
  `savePlayer`，属预期增量）。
- `save-player-cas` 用例3：`final.player.markers` 是 DB 归一化后的 JSON 字符串（含 活力2/使用活力 默认），
  断言改为 `JSON.parse(final.player.markers).toMatchObject({活跃度:9})`。
- `exp-normalize`：其 Prisma 桩原模拟旧 CAS（`where.id_version`）、不模拟 `$use` 自增，CAS 移除后 version
  不前进 → 1 failing；桩改为模拟 `$use` 自增 version 后转绿（10/10）。
- `_audit_writes.mjs` 计数模式 `withUserLock`→`enqueueUserWrite`；`docs/player-state-architecture.md`
  重写为「无锁、无 CAS」纯 Actor 表述（覆盖矩阵、ScheduleService 收口、门禁基线 219 均更新）。

### 验证结果
- `npx tsc --noEmit`：EXIT 0。
- 全量单测（排除 integration）：**540/541 通过**。唯一失败 `onboarding-flow`（真实远程库 e2e，教程文案断言，
  环境相关），与本次重构无关。
- 教训：`withUserLock` 命名本身会误导后人以为需要锁/CAS；串行邮箱（Promise 链）语义要写进注释与文档，
  否则"无锁"承诺会被命名背叛。
