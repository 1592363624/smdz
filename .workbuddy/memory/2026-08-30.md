## 纯 Actor 单写者收口：无锁、无 CAS（用户质疑后）

用户指出：上一轮「彻底根治」声称参照 Actor/Orleans/Erlang（消灭并发、串行归属、每玩家一个串行队列、
内部单线程无竞态、**不需要锁也不需要 CAS**），但代码里仍叫 `withUserLock`（锁）且 `savePlayer` 仍有
`(id,version)` CAS 冲突判定——与纯 Actor 不符。选定方案：**路由2写者 + 移除 CAS**。

### 改造
- 命名纠偏：`withUserLock`→`enqueueUserWrite`（per-user Promise 链 = Actor 收件箱，**非互斥锁**）；
  `userLocks`→`userMailboxes`、`lockContext`→`mailboxContext`。8 个源码文件 + 12 个测试桩同步 rename。
- `savePlayer` 移除 CAS：删去 `where:{id,version}` + P2025→抛「玩家数据并发冲突」分支，改为普通
  `update({where:{id}, data})`；version 仅由 Prisma `$use` 中间件自增，`player.version=snapshotVersion+1`
  回写内存快照。无并发写（同用户全经邮箱），无版本分叉风险。
- `ScheduleService.settlePendingMoves` / `cleanupExpiredBuffs` 两条定时器裸写收口：
  `enqueueUserWrite(userId, async()=>{ getPlayerData 重读最新快照→改→savePlayer })`，达成全量单写者统一。

### 验证修复（原 2 失败 + 1 被 CAS 移除连带破坏）
- `architecture-guard`：`RAW_SAVEPLAYER_BASELINE` 217→219（schedule 两条 `prisma.player.update` 合规收口为
  `savePlayer`，属预期增量）。
- `save-player-cas` 用例3：`final.player.markers` 是 DB 归一化后的 JSON 字符串（含 活力2/使用活力 默认），
  断言改为 `JSON.parse(final.player.markers).toMatchObject({活跃度:9})`。
- `exp-normalize`：其 Prisma 桩原模拟旧 CAS（`where.id_version`）、不模拟 `$use` 自增，CAS 移除后 version
  不前进 → 1 failing；桩改为模拟 `$use` 自增 version 后转绿（10/10）。
- `_audit_writes.mjs` 计数模式 `withUserLock`→`enqueueUserWrite`；`docs/player-state-architecture.md`
  重写为「无锁、无 CAS」纯 Actor 表述（覆盖矩阵、ScheduleService 收口、门禁基线 219 均更新）。

## 完整通用 Actor 运行时（单进程内、全部有状态实体）

用户确认「理想 Actor 模型」是最优方案，要求实现**完整的、最优的 Actor 模型**。经 AskUserQuestion
选定范围：单进程内 Actor（推荐）+ 全部有状态实体（推荐）+ 内存持有 + 异步落库（推荐/更纯）。

### 实现（server/src/modules/actor/）
- `types.ts`：`EntityType`/`EntityId`/`actorKey(type,id)='type:id'`/`PersistPolicy`(`writeThrough`|
  `deferred`)/`ActorTypeConfig`(load/save/initState?/persist?)。
- `actor-runtime.ts`：`ActorRuntime`（`@Injectable`,`OnModuleDestroy`）。每 `type:id` 一个 `ActorCell`
  （内存态 + per-key Promise 邮箱 + 单激活 + 脏标记）；串行化靠 **Promise 链（非 Mutex）→ 无锁无 CAS**；
  ALS 重入识别（`currentActorKey`/`peek`），嵌套调用不自杀锁；`run/tell/ask` 写入口；`deactivate`/`flushAll`
  /`flushIdle`（周期落库）/ LRU 驱逐（`lruMax`/`flushIntervalMs`/`idleEvictMs` 可配）；`run` 执行后按策略
  落库（writeThrough 立即、deferred 仅标脏）。
- `coordinator.ts`：`coordinate`/`coordinateMany` 按 `actorKey` 字典序**确定性排序**获取邮箱，打破
  A↔B 跨实体死锁环路（交易/公会银行/战斗双方）。
- `builtin-types.ts`：`registerBuiltinActorTypes(runtime, prisma)` 注册 monster/map/vehicle/shopitem
  （各自独立表，load=findUnique、save=去 createdAt 整行 update、persist=writeThrough）。
- `actor.module.ts`：`@Global` 提供 `ActorRuntime` 单例；`ActorBootstrap.onModuleInit` 调
  `registerBuiltinActorTypes`（只登记配置、不触库，安全）。

### PlayerService 接入
- `GameModule` 导入 `ActorModule`；`PlayerService` 注入 `@Optional() ActorRuntime`、`implements OnModuleInit`。
- `getPlayerData` 优先 `peek('player', userId)` 命中缓存；`savePlayer` 在 Actor 内分支只改内存态 + `markDirty`
  （抽 `buildPlayerUpdateData` 纯函数 + DB-only `persistPlayer` 防递归）；`enqueueUserWrite` 委托
  `actorRuntime.run('player', userId, fn)`；`onModuleInit` 注册 `'player'` 类型（复用 getPlayerData/persistPlayer）。
- 无 ActorRuntime（测试桩手工 new）时全部回退原兼容路径，行为不变。

### 验证
- `tsc --noEmit`：EXIT 0。
- 新增 `test/actor-runtime.spec.ts`（8 项：串行执行/单激活/peek 缓存命中/writeThrough 即时落库/
  deferred+deactivate 落库/未激活 peek undefined/LRU 驱逐/coordinate 防死锁与确定性）：**8/8 通过**。
- 全量单测（排除 integration-*/onboarding-flow/full-game/combat-formula 等需实库的集成 spec）：
  **546/546 通过**（55 suites，EXIT 0），高于先前 540 基线，无回归。
- 集成 spec（boot AppModule 需实时库）在本沙箱因无 DB 崩溃（process.exit(1)），非本次改动所致：
  `ActorBootstrap.onModuleInit` 仅登记配置不触库、DI 无 "Nest can't resolve" 报错、AppModule 正确 import
  GameModule 加载 ActorModule；属运行环境限制。
- 文档：`docs/actor-runtime.md`（新建，完整设计/模块布局/生命周期/协调者/边界）+ `docs/player-state-architecture.md`
  第 6 节新增「通用 Actor 运行时」指针段落。

### 边界（写入文档第 7 节）
- 单进程内保证串行；水平扩容需加「实体亲和路由」或分布式邮箱（已预留 type+id 稳定键）。

## 诚实边界：「完全 Actor 化 / 无锁无快照覆盖」是否成立

用户追问「项目是不是已经完全是 Actor 模型、没有锁和快照覆盖问题了」。结论（证据驱动，非凭记忆）：

### 成立的部分（漏斗内彻底干净）
- 通用 Actor 运行时已落地：per `type:id` 的 `ActorCell`（内存态 + per-key Promise 邮箱 + 单激活 + 脏标记），
  串行化靠 Promise 链 → **无锁、无 CAS**。
- **指令漏斗 + 定时任务** 走 `enqueueUserWrite` → `ActorRuntime.run`（47 处 `enqueueUserWrite` 调用点）。
  漏斗内：peek 深拷贝只读快照 / peekLive 仅箱内可见 / 落库仅在 dirty 且 fn 成功（全有或全无）/ markers 按 key 并集合并
  → **无快照覆盖、无丢失更新、无锁**。

### 不成立的部分（全局尚未 100%）
- grep 实测仍有 **53 处直接 `prisma.player.update`（非 spec）**，其中：
  - 1 处是 `player.service.ts:617` 的合法落库 sink（Actor run 收尾调），不计绕过；
  - 1 处是 `game-sync/write-context.ts:21` 注释，非真实调用；
  - 其余 **~51 处真实裸写绕过 Actor 邮箱**：
    `item-system.service.ts:24`（完全没 import/用 `enqueueUserWrite`/`actorRuntime`）、`item.service.ts:8`、
    `player.service.ts:4`（handlePlayerDeath/addItem/removeItem/map 自动修复）、`admin.service.ts:5`、
    `game.service.ts:4`、`familiar-system.service.ts:2`、`dungeon.service.ts:2`、`task.service.ts:1`、
    `schedule.service.ts:1`。
- 这些路径在 Actor cell 进行中时仍能读到旧内存快照并并发写库 → 失去单一写入者保证，**快照覆盖/丢失更新风险
  在「这些代码路径」上仍然存在**（漏斗内没有）。`$use` 中间件仍自增 version 不会崩，但不提供单写者串行化。
- **门禁盲区**：`architecture-guard` 只数裸 `savePlayer(` 调用（基线 219），**拦不住裸 `prisma.player.update`**，
  故这 ~51 处能静默绕过门禁。门禁应补一条「裸 `prisma.player.update`（`player.service` 落库 sink 除外）禁止新增」。

### 要达到真正「完全体」
- 把 ~51 处路由进 `enqueueUserWrite`/`ActorRuntime.run`（最高收益：`item-system` 的 24 处）。
- 门禁补裸 `prisma.player.update` 计数；admin 端点如需刻意带外写入，应显式标注豁免。
