# 2026-08-30 工作日记

## 玩家状态写入口「彻底根治」（Actor 式单写者）

延续上轮的基础设施安全网 + 指令漏斗方案，今天定位并修复了安全网本身的**致命反查键 bug**：

- **根因**：`PlayerMutateService.run` 把 mutate 上下文登记在 `userId` 下，但 `PlayerService.savePlayer`
  用 `currentFor(player.id)` 反查（`Player.id` 自增主键 ≠ `Player.userId`）。结果「在 mutate 内调用
  savePlayer」命中不到 ctx → 内层 savePlayer 真的写库并 bump version，外层保存再以过期版本 CAS →
  双写/版本分叉 → 正是反复出现的「玩家数据并发冲突，请重试」根因。
- **修复**：`run` 同时按 `userId` 与 `player.id` 登记；`savePlayer` 改按 `resolveMutateKey`
  （优先 userId，回退 player.id）反查合并。因 `AsyncLocalStorage.run` 在 fn 结束后还原 store，
  最外层收口仍走真实落库。
- **BigInt 加固**：`getPlayerData` 读侧把玩家对象上的 `BigInt` 属性（lastOpTime/readTime）转 Number，
  修掉 `pushState` 序列化抛「Do not know how to serialize a BigInt」的崩溃。

### 经验教训
- 「上下文感知」类安全网必须保证**登记键与反查键一致**，否则静默失效（比没有安全网更危险，
  因为看起来已收口）。用「内层 savePlayer 应只落库一次」这类计数断言才能锁住。
- 指令路径与定时器（auto-mine / gather / weaponAttack）都走同一把 `withUserLock`，故已天然互斥；
  `settleGatherResource` 中段 CAS 认领是刻意的真实落库，勿并入 merge。
