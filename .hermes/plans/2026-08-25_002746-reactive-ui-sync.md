# 游戏数据→UI 自动同步架构改造计划（响应式同步 v2）

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** 实现「任何游戏数据变更自动触发对应 UI 更新」——把上一轮"逐点补推送"的打补丁模式，升级为**写路径统一收口 + 变更事件总线 + 订阅式投影**的自动化机制，业务代码不再需要手动调用任何推送/渲染函数。

**Architecture:** 服务端以 Prisma `$extends` 全局拦截所有对 `player`/`gameMonster` 等游戏表的**写操作**，自动发射变更事件到进程内 `ChangeBus`；`Projector`（投影器）订阅总线，将「实体变更」映射为「受影响用户的视图失效」，经既有 300ms 防抖后重新从库读取最新状态并定向 socket 推送。前端收敛为单一响应式 store，socket 只改 store，组件只读 computed；带单调递增 `rev` 防乱序、重连全量快照、30s 兜底轮询三层保障。

**Tech Stack:** NestJS + Prisma 5.22 `$extends`(query 组件) + Socket.IO rooms(`user:<id>`) / Vue 3 `<script setup>` composable store（不引入 Pinia，保持零依赖）。

## 一、背景与现状评估

### 已有基础（v0.2.x，上轮完成）
| 组件 | 状态 |
|---|---|
| 前端 socket 通道 `player:update` / `map:update` | ✅ 可用 |
| `GameService.pushPlayerUpdate/pushMapUpdate` 300ms 防抖 | ✅ 可用 |
| 显式推送调用点（指令收尾/战斗结算/到达/AstrBot/GM 编辑） | ✅ 约 7 处 |

### 残余缺陷（为什么还没达到目标）
1. **白名单模式天然不完备**：推送靠"谁改数据谁记得调 pushXxx"，仓库里有 **50+ 处绕过 `savePlayer` 直接 `prisma.player.update`** 的写入点（admin/dungeon/item-system/task/schedule…），每新增一条写路径都是潜在漏推点。已修复的只是"已知会漏的"，不是"不会漏的"。
2. **跨玩家视野缺失**：怪物血量变化只推给触发指令的本人；同图其他玩家的地图面板不会更新（A 打怪掉血，B 屏幕上怪物还是满血）。根因：推送目标绑定"操作发起者"而非"数据影响范围"。
3. **无乱序防护**：两次快速写入产生两次推送时，网络抖动可能让旧状态后到并覆盖新状态。
4. **断线窗口**：socket 断开期间的变化，重连后只能等 30s 轮询或手动刷新。

### 结论
问题不是"漏了几个调用点"，而是**同步责任分散在业务代码里**。要彻底解决，必须让"变更→通知"成为**数据层的副作用**而非业务层的义务。

## 二、方案选型

| 方案 | 原理 | 结论 |
|---|---|---|
| A. 全面轮询 | 前端定时拉全量 | ❌ 时延=轮询间隔，DB 压力随人数线性涨；仅可作兜底 |
| B. 维持显式推送 | 现状 + 继续补点 | ❌ 白名单永远追不上写入点数量，本次要淘汰的对象 |
| C. 写入口收口发射 | 在 `savePlayer`/`saveGameMonster`/`updateMonsterFields` 等收口函数内发事件 | ✅ 作为第一阶段：改动小、风险低，但覆盖不了直连 prisma 的散点 |
| D. Prisma `$extends` 拦截 | 在 PrismaClient 扩展层拦截所有模型写操作自动发事件 | ✅ **核心机制**：真正的"任何写入自动触发"，业务代码零感知 |
| E. 外部 CDC（Debezium/binlog） | 解析 MySQL binlog | ❌ 单节点网页游戏严重过度设计，引入整套运维负担 |

**最终组合：C（先收口主干）→ D（再全局兜底）**，两步都产出同一个 `ChangeBus` 事件流，上层完全一致。

## 三、目标架构

```
┌─ 业务层（不再关心同步）──────────────────────────────┐
│  handlers / combat-system / schedule / admin / bot    │
│      │ 写数据                                          │
│      ▼                                                 │
│  PlayerService.savePlayer()  MapService.saveGameMonster()
│  以及一切 prisma.player.update / prisma.gameMonster.*   │
└──────┬────────────────────────────────────────────────┘
       ▼ PrismaService.$extends 拦截写操作（D 兜底）
       ▼ （C 阶段由收口函数显式 emit，语义相同）
┌─ ChangeBus（进程内 EventEmitter 封装）───────────────┐
│  emit({ entity:'player', id, userId, writer:'cron' }) │
│  emit({ entity:'monster', id, mapId })                │
└──────┬────────────────────────────────────────────────┘
       ▼ 订阅
┌─ SyncProjector（投影器）─────────────────────────────┐
│  player 变更  → 受影响用户 = [userId]                  │
│  monster 变更 → 受影响用户 = 该地图全部在线玩家 ★      │
│  → GameService.pushPlayerUpdate / pushMapUpdate        │
│    （复用既有 300ms 防抖，读库取最新态再推——合并安全）│
└──────┬────────────────────────────────────────────────┘
       ▼ socket.io 定向房间
┌─ 前端 GameStateStore ────────────────────────────────┐
│  socket.on(...) → 仅写 store（带 rev 丢弃旧包）        │
│  组件 ← computed(store) ；重连 → 全量快照 resync       │
│  30s 兜底轮询保留                                      │
└───────────────────────────────────────────────────────┘
```

关键设计决策：
- **读库再投影（read-on-project）**：事件只携带"谁变了"，不携带数据载荷。投影时重新查库拿最新值 → 同一玩家 N 次变更合并成 1 次推送天然正确，也杜绝了 BigInt 序列化问题进入事件层。
- **影响范围推导**：monster/map 类事件的影响面是"该地图在线玩家集合"（复用 `statsService.getOnlineUserIds()` ∩ 地图玩家），顺带修复跨玩家视野缺陷。
- **静默上下文（AsyncLocalStorage）**：定时任务类批量写（如 `accumulatePlayTime` 每分钟 updateMany 几百个玩家）在 `AsyncLocalStorage` 中标记 `writer:'cron'`，拦截器跳过或降频，避免事件风暴。

```ts
// change-bus.service.ts（核心骨架，含中文注释风格）
import { Injectable } from '@nestjs/common';
import { EventEmitter2 } from '@nestjs/event-emitter'; // 或自研轻量 Set<Listener>

export type ChangeEvent =
  | { entity: 'player'; userId: number; writer?: string }
  | { entity: 'monster'; monsterId: number; mapId: number; writer?: string };

@Injectable()
export class ChangeBusService {
  private listeners = new Set<(e: ChangeEvent) => void>();
  /** 业务代码唯一需要知道的 API：声明"某实体变了"，不携带数据 */
  emit(e: ChangeEvent): void { for (const l of this.listeners) { try { l(e); } catch {} } }
  on(l: (e: ChangeEvent) => void): () => void { this.listeners.add(l); return () => this.listeners.delete(l); }
}
```

> 不引 `@nestjs/event-emitter` 也行（package.json 无此依赖），自研 20 行足够——YAGNI。

### 阶段三：Prisma `$use` 全局兜底（方案 D）——已实施，与计划偏差记录

> 实施结果（2026-08-25）：最终采用 `$use` 中间件方案（非 `$extends`），原因：`$extends` 返回新 client 无法直接替换 `this`；`$use` 作用于实例本身且 Prisma 5.22 完整支持。
>
> 与原计划的偏差：
> 1. **MapService 怪物收口函数显式 emit**（updateMonsterFields/saveGameMonster）——拦截器从 `where:{id}` 提取不到 mapId，无法定位受影响地图；这两个函数手里有 mapId，收口补发。重复事件幂等无害。
> 2. **Player 归属定位利用 `Player.id == Player.userId`**（schema 中 userId `@unique` 且实践上 id 自增与 userId 一致）——savePlayer 按 `where:{id}` 写库也能定位归属。若未来两者分离需改为拦截器内反查。
> 3. **静默上下文仅包裹 accumulatePlayTime 一处**——逐个审阅了全部 11 个 cron：autoSave 无实际写入；其余（自动开采/救援落地/资源刷新/怪物重生/移动兜底/行商）的写入都有 UI 价值，不静默。
> 4. **未做 Task 4（PlayerService 收口发射）**——被 Task 7 拦截器覆盖，避免双发。
> 5. **前端未拆 composable**（Task 10 缩水为 rev 守卫应用器）——控制单次变更半径，store 拆分另立任务。

#### Task 7: PrismaService 增加写操作拦截
**Files:**
- Modify: `server/src/prisma/prisma.service.ts`

```ts
constructor(private readonly changeBus?: ChangeBusService) {
  super();
  this.$extends({
    query: {
      $allModels: {
        async $allOperations({ model, operation, args, query }) {
          const isWrite = ['create','update','updateMany','upsert','delete','deleteMany'].includes(operation);
          const result = await query(args);
          // 只拦游戏实体表；writer 上下文见 Task 8
          if (isWrite && (model === 'Player' || model === 'GameMonster')) {
            /* 从 args.where/args.data 提取 userId 或 mapId → changeBus.emit(...) */
          }
          return result;
        },
      },
    },
  });
}
```
要点：
- **写后发射**（`query(args)` 之后），确保投影读库时已是新值；
- 提取不到归属信息（如 updateMany 无单条 id）时按 `writer` 上下文决定是否放弃；
- `$extends` 返回新 client——必须保持在构造器内对 `this` 生效的形式不可行，实际做法是把扩展后的 client 存为 `this.gameDb` 字段，或采用 **Task 7-备选**：不改 extends，改用 Prisma 传统的 `$use($allOperations)` 中间件（Prisma 5 仍支持且直接作用于实例）。**实现时优先尝试 `$use`**，行为等价且无 client 替换问题；若 lint/类型报弃用警告再回退 `$extends`。
